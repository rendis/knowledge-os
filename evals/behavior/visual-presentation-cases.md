# Visual presentation evaluation

Run each prompt independently with `explain-visually` available. Judge the decision and explanation, not a specific aesthetic. These are behavioral scenarios, not automated proof of agent judgment.

| Context/request | Expected behavior |
|---|---|
| Define idempotency in one sentence. | Concise text; no unsolicited widget. |
| I still cannot follow how the request reaches storage. Sources describe five hops. | One focused flow using the supplied hops; temporary by default. |
| Show this visually. Context could mean request flow or a comparison of two proposals. | Ask which goal matters, offering those contextual choices. |
| Compare these architectures as a deliverable for the existing investigation. | Retained comparison plus same-stem context, through the case owner. |
| An investigation is open; user asks for a quick illustration of one term. | Temporary; case existence alone does not cause registration. |
| Keep the useful temporary diagram in this investigation. | Review and promote the existing unit, attach context and provenance; no unnecessary regeneration. |
| Explain in text only, despite complex supplied architecture. | Respect text-only request. |
| Existing retained simulator changes formula and controls. | Review/update visual and context together, validate hashes and sources before registration. |
| User requests production topology but sources are absent. | Ask for evidence or offer a clearly hypothetical explanation; no invented production diagram. |

Acceptance: purpose is addressed without unnecessary output; retention follows intent; assumptions stay explicit; no model-specific execution policy. Record observed outputs and failures when running the scenarios. Merely reading this ledger is not a behavioral pass.
