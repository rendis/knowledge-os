# Consult another domain vault

Use this procedure when the active question needs evidence from another vault. The originating workflow retains ownership; consultation is read-only and requires no persistent registry or new case.

## Discover and bind

1. State the missing question and the connection that makes the other domain relevant. Discover candidates while exploring repositories within authorized source roots, or use a vault explicitly identified by the user. Keep discovery within the configured repository discovery depth or the user's explicit scope; do not scan the machine or acquire repositories to find vaults.
2. Distinguish a domain relationship from an accessible vault. An API, message resource or database reference is a lead, not proof of the other endpoint or permission to access it. Use available repository identity and vault markers to locate a candidate; directory names alone do not establish identity. No advance registration is required.
3. Before reading destination domain content or running its tools, explicitly read its root `AGENTS.md`, then `AGENTS.personal.md` if present. A directory change does not prove those instructions were loaded. Missing personal instructions are valid; a missing or unreadable `AGENTS.md` blocks that destination consultation. Follow the destination's identity and orientation procedure, including relevant scope and skill references, without assuming kernel or version equivalence. Use its resolver when instructed, with the destination path explicitly bound. Resolve ambiguous candidates with the user instead of selecting by name or recency.

## Consult within the destination

4. Keep origin and destination roots, source bindings and instructions separate. Destination instructions govern work there, subject to current user instructions and higher-priority constraints; they do not expand authorization or replace origin preferences when returning. A conflicting requirement blocks only the dependent work. The read-only consultation authorizes no configuration repair, personal-preference persistence, case creation, source acquisition, operational execution or other writes. Report a required mutation or missing access and continue independent origin work.
5. Follow the destination's navigation and evidence method for the bounded question. When consulting an investigation, use its read-only case loader and preserve overlay provenance and disclosure restrictions. Destination access does not authorize copying private evidence into the origin or a shareable answer. Return only information permitted for the intended audience; retain restricted evidence in its owning store.
6. Verify each claimed connection against exact endpoint/resource identity, contract, direction and environment. Separate documented or configured relationships from deployed or functionally observed behavior. If the two vaults disagree, report both sources and the unresolved discrepancy; do not silently choose or rewrite either side.
7. Follow another vault only when it can materially answer the original question within authorized access. Track visited canonical vault identities and questions in task-local context. Reuse prior results for the same vault/question, including an A → B → A return; stop cycles and hops that cannot change the answer. Delegation is optional and follows the active execution contract; a delegate receives the same bounded question, destination entry requirements and read-only scope.

## Return and finish

Return the answered question, destination identity, consulted document paths and source references, revision when available (including relevant uncommitted changes) or observation date, findings, evidence limits and applicable disclosure restrictions. Distinguish unavailable access, ambiguous identity and insufficient evidence from a verified absence of a relationship.

Restore the origin bindings and resume its workflow. Consultation creates no durable record by itself. When origin publication is separately authorized, retain a concise domain-relevant synthesis and resolvable destination references through the origin's evidence and review gates. Qualify references by vault identity and relative path or canonical repository URL; a bare wikilink can resolve to an unrelated same-named local note. Keep destination internals canonical there and private machine paths out of shared notes.

Finish when the bounded question is answered with traceable, disclosable evidence or the precise missing evidence/access is reported. Preserve independent progress and leave both vaults unchanged by the consultation.
