# Correct a map from investigation evidence

Apply when an investigation establishes a materially incorrect claim, wrong flow or relationship, or missing main-flow information in existing canonical notes. Optional detail is not a mapping defect. A suspicion, inaccessible source, or absent search result alone does not establish an error.

1. Identify the affected note/claim, the previous assertion or material omission, and exact evidence supporting the correction. Compare source revision and environment: a later implementation change or a different deployment does not prove the old observation was false. Preserve valid historical observations and label their scope; reconcile a newer state through the ordinary delta path.
2. Check existing authorization. Case-write authority alone does not authorize canonical vault writes. If the session already authorizes updates to the affected vault, continue without asking again. If it is read-only or lacks that authority, keep the canonical notes unchanged and report the exact proposed correction and its evidence. Request missing authority only for the dependent write, after preparing the proposal; continue independent investigation work.
3. For an authorized, confirmed defect, invoke **Promote** in the same iteration with the correction package: old assertion, supported replacement, canonical paths, source revision/environment, evidence and affected relationships. `map-ecosystem` owns the bounded write and independent final-note review. Reuse the accepted map and existing evidence; inspect only the affected flow, claims and directly impacted notes. Unchanged source HEAD does not block a demonstrated correction. Do not remap the ecosystem or reopen closed source packages.
4. Apply `90-Meta/evidence-policy.md` to the precise replacement claim. Correcting a source-level map of inspected main/master implementation or configuration uses the source-map rule under every profile; successful deployment is not required. This does not promote proposals, unmerged development or unverified production behavior. Stronger deployed/functional assertions retain their evidence requirements. If evidence disproves a claim but does not establish a replacement, review removal or qualification of that specific claim and retain the exact unknown instead of inventing a replacement.
5. Finish the correction with the normal publication checks, including current-byte verification. Then save the case through its ordinary transaction, naming the canonical result, evidence boundary and observed checks in the existing outcome/history fields. Reconcile affected drafts or mark them stale. Canonical publication and case saving are separate transactions: after interruption, inspect the current state and reuse a completed correction rather than repeating it.

An authorized, evidence-backed correction is part of the iteration, not a suggestion deferred to the investigation's final close. If review, authority, access or concurrent changes prevent publication, record the exact remaining correction and reason; do not report it as documented. Unrelated questions may continue and unresolved suspicions remain labelled contradictions. Case closure still follows its stated objective and must accurately disclose any deferred correction.
