# Scheduled vault refresh

Guide a scoped vault refresh, whether requested manually or invoked by a scheduler. The team chooses when it runs, what sources it covers and how approved vault changes are published; this skill supplies the shared evidence, mapping and reconciliation method. Do not create a recurring task from a suggestion alone.

## Team bindings

Keep team choices in the consumer vault and its scheduling configuration, not in this managed skill. Read portable source identities and the evidence profile from `instance.yaml`; resolve each actual source checkout from the current `source_context` through `<VAULTCTL> config locate --vault "<VAULT_ROOT>" --remote "<REMOTE>"` before reading it. Local source roots and clone authority belong to `.knowledge-os-config.yaml` and its `configure-workspace` owner. Resolve team release procedures through `manage-operational-workflow` and repository-specific Git rules through `manage-git-workflow` and applicable notes in `60-Operacion/Git/`. The team may choose a manual run, a periodic trigger, a PR path, an authorized direct push or a review-only result. No cadence, scheduler, branch strategy, merge method or publication destination is universal. Personal interaction preferences belong in `AGENTS.personal.md`; they do not replace team policy or grant Git authority.

## Schedule setup

When the user accepts a recurring refresh, agree on its cadence, target vault, source scope, authorized vault and case writes, permitted Git effects or review-only mode, and notification preference. Read the evidence profile from the vault's `instance.yaml` on every run. Save the chosen scope, effect authority and any applicable versioned team procedure reference in the available scheduler's task prompt or configuration and have each run invoke this skill. Read back the saved task to confirm them; do not infer push, PR, merge, or deployment authority from scheduling alone.

## Run contract

Identify the vault, source repositories, current evidence profile, publication path and authorized effects before a write. A recurring task must carry its chosen cadence and source scope, plus vault-write authority, permitted case updates, allowed Git effect classes or review-only mode, and any applicable team procedure reference. Resolve applicable procedures and current policy on each run; a changed procedure cannot expand saved authority. Missing authority permits a read-only report, not an inferred write. The source repositories remain read-only; publishing this vault does not deploy a source application to production.

Use one isolated checkout or worktree for the run when the scheduling environment provides it. Preserve unrelated work. A local lock can avoid two runs in that checkout; it does not coordinate other developers or machines. Treat the remote repository state and applicable Git policy as the shared publication boundary.

## Refresh cycle

1. **Bind the vault and publication policy.** Resolve the vault through `90-Meta/vault-resolution.md` with `<VAULTCTL> config resolve --vault "<EXPLICIT_PATH>"` and its repository Git root. Use `manage-git-workflow` to inspect the vault's repository instructions, every potentially applicable specific note under `60-Operacion/Git/`, and current branch, upstream, remote and PR rules before deciding on fetch, pull, commit, push or PR. A cell Git note applies to the vault repository only when it explicitly includes that repository. Resolve any applicable release procedure through `manage-operational-workflow` instead of inventing one.
2. **Reconcile the starting point.** When the vault has a configured publication remote, compare the checkout with its tracking upstream or the intended remote/base ref before mapping. Follow the selected repository policy for fetch and integration; preserve unrelated local changes. Resolve a divergent or conflicting starting state before mutating canonical notes. A branch without a tracking upstream may use the team's authorized first-push or PR path after its exact remote and base are verified. When no remote/base can be bound, record that cross-developer freshness cannot be verified and continue only with authorized local or review-only work. Never select a merge/rebase strategy solely to clear divergence, and never force-push as recovery.
3. **Select the knowledge delta.** Use `synchronize-ecosystem` inventory and [associated investigation evidence](../map-ecosystem/references/investigation-context.md). Also use `manage-investigation`'s `list` and read relevant published cases in the selected cell scope, including cases with no changed repository or repository link. Include repository changes without a case, changes clarified by a case, and eligible case evidence without a source change. A case must be relevant by claim, component, evidence identity and environment; publication or closure alone is not proof of production. Apply `90-Meta/evidence-policy.md` claim by claim. For automatic absorption of investigation knowledge, require evidence that the claim applies in production; source-only repository maps remain labeled as source observations under that policy and do not promote unverified case conclusions. Compare each case register ID and evidence identity/revision or observation date with its Readiness disposition and verified canonical destination before proposing a write. Existing coverage is a no-op for that claim, not a reason to re-extract its repository or reopen a closed sync package. An unpublished case can identify a pending opportunity but cannot supply a versioned canonical write.
4. **Map and absorb.** Run or resume `synchronize-ecosystem` for changed source packages. Route investigation-only contributions through `manage-investigation`'s **Promote** or **Absorb** route and `map-ecosystem`'s ordinary documentation transaction after the local sync; keep external evidence outside sealed Git packages. Use the independent review and publication gates of those workflows. Return verified destinations, register IDs, source boundaries and review results to `manage-investigation`; let that owner update the case's existing outcomes and History only with case-write authority. Without a durable destination or the required record, report the contribution as pending rather than absorbed.
5. **Validate and publish when authorized.** Run the relevant vault checks and inspect the exact documentation and case diff. Before a remote effect, refresh the exact destination or base ref and re-evaluate the applicable policy and authorized effects through `manage-git-workflow`; an unresolved remote, ref, policy or authority blocks that effect. Before an authorized local commit, recheck applicable policy and local state. Integrate concurrent contributions only when both Git state and the combined documented meaning are valid. If a conflict, stale source, changed policy or ambiguous overlap appears, preserve the work and report the needed review. Follow the team's authorized review, PR or direct-publication path, including an explicit first push when allowed; verify its remote ref or PR after writing. A local sync receipt is not remote publication proof.
6. **Close the run.** Report the inspected source revisions, claims newly documented, claims already covered, unresolved candidates, case records updated, checks, and Git publication result. An unchanged run records a verified no-op. Reuse recorded sync state on retry; a publication failure does not restart semantic extraction. Scheduled runs stay quiet when nothing actionable changed unless the saved notification preference requests a status report.

Complete when every selected source and case contribution has a supported disposition, local checks pass for applied changes, the team's selected publication or review-only result is verified or its blocker is explicit, and no source repository was mutated.
