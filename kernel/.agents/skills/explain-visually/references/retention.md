# Retention and ownership

## Temporary

Temporary means outside the durable investigation record, not automatically deleted. A useful temporary visual can later be promoted after retention intent and the checks below are satisfied. Create a unique OS temporary directory with an `explain-visually-` prefix, outside the vault. Track the exact directory and files in the task. It is unversioned and must not be referenced from durable notes. Keep a delivered preview available while the user reviews it. When discarded, or after a preserved copy is verified, remove only the known generated files in that exact owned directory; reject symlinks or unexpected contents instead of recursively deleting an uncertain target. Report cleanup actually performed. Closing a chat has no guaranteed cleanup hook; never claim automatic deletion without one.

## Retained investigation artifact

A request for a visual as part of the investigation deliverable, or an explicit request to attach, preserve or version it, establishes retention intent; a case's mere existence does not. Generate in staging first. Review the entire payload, including hidden HTML data, scripts, source tables and file paths for shareability. Exclude secrets and private overlays from public output. If restricted data is necessary, return a protected reference through the existing case owner rather than inventing a public copy or a new private store.

Hand the reviewed files and provenance to `manage-investigation`. Its record contract owns public artifact naming, hashes and case registration. The target remains the existing case's `artifacts/`; register the generated view as derived, with links to its supporting source IDs and assumptions. Treat the visual and its same-stem Markdown as one reviewed unit, for example `A-007-request-flow.html` and `A-007-request-flow.md`. Use `assets/visual-context.md` as a brief starting point. The context explains why the visual was needed, the intended question (not a transcript), what it represents, how to read/use it, sources or source IDs, assumptions, limitations, and generation date or source revision. Keep it proportional to the visual and use the cell note locale.

The retained visual follows the same case-artifact lifecycle as a script or other derived method: its reviewed revision stays with the case while the investigation is active. Before case retirement, a visual needed by a current note moves to that note's resources; a visual used only to explain the historical case may remain in the exact Git snapshot. Record that disposition through `manage-investigation`.

Multiple representations of the same content, such as HTML and SVG, may share this Markdown; list every delivered representation and supporting local data file with its SHA-256 in the context metadata. Include relative links to each file in the prose. An embedded Mermaid diagram already in Markdown uses that same file for context, lists no separate visual file, and never hashes itself.

Before delivery run `python3 scripts/check_visual_context.py PATH_TO_CONTEXT.md`. This checks file correspondence and links, not whether the prose is true. Review meaning and source fidelity separately. The case owner records the context file's hash in the case register; the context records the other files' hashes, avoiding a circular self-hash.

For updates, stage the whole unit, review the new visual and explanation together, refresh hashes only after that review, and validate before replacing the retained unit. A hash mismatch means unreviewed drift; never fix it merely by recalculating the hash. Preserve the prior complete unit until the replacement and case registration succeed; restore it if registration fails. Keep identity for revisions of the same purpose, and use a new attachment ID for a materially different purpose under the case contract. Regeneration preserves the previous reviewed result until the replacement is checked. Compare source revisions before reusing a derived view; mark it stale when the source changed and validity has not been re-established.

## Stable note or review collection

Stable knowledge publication goes through `map-ecosystem` and its evidence profile. A proposal may remain a versionable investigation artifact without becoming current-state documentation. For a user-requested standalone review collection, use the explicitly selected output directory and an index with relative links; do not fabricate a case. Source/template fixtures in this distribution belong outside consumer knowledge directories. Retained or versionable means ready for Git review, not already committed or published.
